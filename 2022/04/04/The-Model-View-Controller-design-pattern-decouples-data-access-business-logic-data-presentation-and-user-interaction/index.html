The Model-View-Controller design pattern decouples data access, business logic, data presentation, and user interaction

Posted on 2022-04-04 | In Java | Views
CS1103 Discussion Assignment Unit 7.

Introduction

In this discussion, I will first introduce the definition of MVC and then explain how Model-View-Controller (MVC) “decouples data access, business logic, data presentation, and user interaction” (UoPeople, n.d.). Next, I will use concrete code to illustrate these advantages further. Finally, I will make a summary.

1. Definition and Explanation

The Model-View-Controller (MVC) pattern divides an application into three components: Model, View and Controller. Different parts have different responsibilities. Specifically, the Model is the data and the rules (business logic) for processing that data (Pastor, 2010). The view is the display interface responsible for showing the data received from the Model (Pastor, 2010). The controller is used to “coordinate interactions between the Model and View” (Banas, 2013). In other words, “it usually calls the appropriate Model for the task and then selects the proper view. It contains a lot of internal-organizational logic (more like housekeeping)” (Pastor, 2010).

Handling user requests using MVC pattern (Pastor, 2010)

I got the image above after modifying the figure from Pastor’s blog. It is beneficial for how MVC decouples user interaction, data presentation, business logic, and data access. The specific explanation is as follows: First, user interaction is in charge of the Controller. Specifically, in processes 1 and 7, when the user sends a request, the Controller will call the Model to process the data and the View to display the results. Second, data presentation is the View’s responsibility. Concretely, in steps 5 and 6, the Controller will call the appropriate View to display the data from the Model. Third, business logic is mainly handled by the Model. More specifically, as shown in processes 2 and 4, the Model will process the data according to specific rules after receiving the call request from the Controller. Fourth, data access is shown in process 3. The Model needs to read data from the database or hard disk before processing it. Based on the above explanations, we can see those different components of MVC are responsible for data access, business logic, data presentation, and user interaction, respectively. Therefore, MVC decouples these four functions nicely.

2.2. Outputs

The above code implements an addition operation and displays the result using a Swing component. The author created four classes using the MVC design pattern: CalculatorModel, CalculatorView, CalculatorController, and MVCCalculator. Specifically, 1) the CalculatorModel class corresponds to the Model, which is mainly responsible for data access and business logic processing. In this example, the Model performs the addition operation. 2) The CalculatorView class corresponds to the View and is responsible for the data presentation, as shown in the Outputs. 3) The CalculatorController class corresponds to the Controller, which is mainly responsible for interacting with the user and coordinating the interaction between the View and the Model. In the example, the Controller call the Model to get the calculation results and sent it to the View for display. As can be seen from the above description, the three parts of MVC correspond to three classes, and each of these classes is responsible for business logic, data access, user interaction, and data presentation, respectively. Therefore, The MVC design pattern decouples business logic, data access, user interaction, and data presentation well.

3. Conclusion

In conclusion, Model-View-Controller (MVC) consists of Model, View and Controller. The Model is responsible for data access and business logic, the View is responsible for data presentation, and the Controller is responsible for user interaction. Therefore, the MVC design pattern decouples the above four aspects nicely.
